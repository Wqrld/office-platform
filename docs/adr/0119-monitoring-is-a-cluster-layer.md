# 0119 — Monitoring is a leaf layer that alerts on symptoms; on by default

**Status:** proposed · **Date:** 2026-10-19 · **Amends:** `history/design/02-architecture.md`
(Observability), `history/design/10-verification.md` ("Observability is generated, never
hand-built")

## Context
The design set planned kube-prometheus-stack, with ServiceMonitors and PrometheusRules
generated by the surround from app values. None of it was built. The CNPG cluster says
"no Prometheus on this cluster yet", and Collabora's ServiceMonitor is off. A running
platform reports its health only through Flux, and Flux reports whether a release
*applied*, not whether its pods are still serving.

The maintenance week showed what that costs. The node rebooted with the kubelet's graceful
shutdown off, and Longhorn's volumes went away while Valkey was still writing. The broker's
AOF ended in a torn write, and Valkey refused to start 293 times over 24 hours. Drive's
Celery workers could not reach the broker, so the task that refreshes Collabora's discovery
stopped. The cached copy expired, and Drive quietly stopped offering to edit documents.
During all of this every Kustomization and HelmRelease was Ready. A user found the outage.
Afterwards the broker sat at 0/0 replicas after its HelmRelease was resumed, because
helm-controller does not correct drift unless asked to.

Each failure in that chain is an ordinary signal: a crash loop, a Service with no endpoints,
a Deployment below its replicas, a front page that stops answering. Nothing was collecting
those signals.

## Decision
- **Monitoring is chosen in `cluster.yaml`, like the cluster services (`0112`).**
  `monitoring.mode` is `platform | external | none`, and `monitoring.email` says where alerts
  go.
  - `platform` adds two layers. `cluster-monitoring` installs kube-prometheus-stack
    (Prometheus, Alertmanager, kube-state-metrics; no Grafana, no node-exporter) into
    `office-monitoring`. `monitoring` brings the blackbox exporter, the rules, the Probes and
    the alert routing once the CRDs exist. There are two layers for the reason `0112` has
    two: a CR cannot be applied before the chart that brings its CRD.
  - `external` is for a cluster whose own monitoring is already watched by someone. It emits
    only the `monitoring` layer: the rules, the Probes, and the blackbox exporter the Probes
    need, which such stacks often lack. Alert routing belongs to the cluster's own
    Alertmanager, so the platform does not touch it, and the schema refuses
    `monitoring.email` in this mode. `preflight.py` checks that the CRDs are there and that
    the cluster's Prometheus selects the platform's objects, since its label selectors often
    ignore them silently. It warns, but cannot ensure, that Longhorn's
    metrics are collected: the rules built on them never fire without those metrics.
  - `none` emits nothing, and `preflight.py` says so. Not `off`: YAML 1.1, which Helm
    reads, turns an unquoted `off` into `false`.
- **The default is `platform`, at every size.** A cluster without alerts is the failure this
  ADR answers, so it must be a choice someone writes down, not where they land by default.
  Every size runs one replica of each component.
- **Monitoring is a leaf: nothing waits for it.** No layer or app `dependsOn` either
  monitoring layer, and nothing outside them emits a monitoring CRD. A chart that will not
  install, or a Prometheus that will not start, therefore blocks no release, and
  `mode: none` changes no other layer's output. Everything the rules need comes from inside
  the two layers or from `cluster-vars`.
- **Nothing is collected unless a rule reads it.** Each metric source arrives with the first
  rule that uses it, and leaves with the last. At this decision that means:
  - **kube-state-metrics:** workloads, endpoints and node conditions.
  - **The kubelet's own endpoint:** volume usage.
  - **The blackbox exporter:** the Probes, and the certificate each host serves.
  - **Longhorn:** a component, emitted when the volumes are Longhorn's.

  Not collected: the control plane (API server, etcd, scheduler, controller-manager,
  kube-proxy, CoreDNS), the kubelet's per-container cAdvisor series, node-exporter, and
  datastore exporters, CNPG's included, and cert-manager. The probes read the certificate
  users are actually served, which is the symptom, and they do so on clusters whose
  cert-manager the platform did not install as well.
  - Node health comes from the kubelet's own conditions (`DiskPressure`, `MemoryPressure`,
    `PIDPressure`, `Ready`), and Longhorn's disk usage covers the disk the volumes live on.
  - Leaving node-exporter out also means nothing here needs host access, so
    `office-monitoring` runs under the same Pod Security level as every other namespace
    (`0102`).
- **The rules alert on symptoms, and the same rule covers every workload.** The `monitoring`
  layer carries one PrometheusRule over the `office-*` namespaces, and the Longhorn
  component one of its own:
  - a pod crash-looping;
  - a Deployment or StatefulSet with no available replica, and, separately, one below its
    desired count for 15 minutes;
  - a Service with no ready endpoints;
  - a node condition other than `Ready=True`;
  - a probe failing;
  - a Longhorn volume degraded or faulted, and a Longhorn disk more than 85 % full;
  - a PVC more than 85 % full;
  - a served certificate within 14 days of expiry, as the probe sees it;
  - a `Watchdog` that always fires, so a silent Alertmanager can be noticed from outside.

  CNPG runs Postgres as bare Pods, not as a Deployment or StatefulSet, so the endpoint rule
  on its `-rw` Service is what watches the database. Its `-ro` Service is excluded, because
  it is empty by design until a size runs replicas. Workloads the platform renders at
  `replicas: 0`, such as Meet's agents and Celery queues, have no Service, and the
  replica-based rules skip a desired count of zero.
- **The probes come from the control plane, not from the apps.** `cluster-vars` already holds
  every public host (`TLS_HOSTS`: the hosts of each enabled app, plus `id` and, with Garage,
  `s3`). One `Probe` in the `monitoring` layer targets each of them at `https://<host>/`,
  through DNS, the certificate, the Gateway and the route, as a user does. It passes on any
  answer below 500 (a 302 to the login, Garage's 403 at its root), and fails on a timeout, a
  TLS or DNS error, or the Gateway's 5xx for a backend that is down. Whether the app behind
  the host works properly is a check specific to that app; see "What this layer is for".
- **Flux reports through Alertmanager under `platform` only.** A notification-controller
  `Provider` of type `alertmanager` and one `Alert`, in `flux-system`, forward failed
  reconciliations of every Kustomization. An `Alert` cannot select every namespace, so an
  app's failing HelmRelease arrives through its layer's health check, which names it. Under `external` the platform does not know the cluster's Alertmanager,
  so `docs/install.md` gives the two objects an organisation adds itself. The endpoint and
  workload rules catch the outages a failed reconcile leaves behind in either mode.
- **The datastore releases turn on drift detection** (`driftDetection.mode: enabled`) on
  `platform/valkey/` and `platform/opensearch/`. A hand-scaled or hand-edited datastore is
  put back, and Flux reports the correction, without waiting for the next chart change.
  `platform/tenants.yaml` keeps the default: what it renders is Jobs, which are immutable
  once created, and objects that operators reconcile, so drift there would be either noise
  or a correction that cannot be applied. Apps keep the default too, because upstream charts
  mutate their own objects too often for drift to mean anything there.
- **Under `platform`, alerts go out by email through the platform's SMTP relay**, the
  `smtp-credentials` Secret Keycloak already uses, read into `office-monitoring` through the
  same ClusterSecretStore. No new secret. External Secrets renders Alertmanager's whole
  configuration from it: an `AlertmanagerConfig` can take the password from a Secret, but
  not the host, username or sender. A webhook receiver can be added later as a Secret
  reference.
- **Prometheus and Alertmanager run at `office-data` priority.** It ranks them above the
  apps, so an application's memory pressure cannot evict the thing that reports it. It does
  not rank them above the gateway or identity, which users need more than they need alerts.
- **The layers keep Flux's substitution off where it would do damage.** Rule annotations use
  `$labels` and `$value`, so the PrometheusRule carries
  `kustomize.toolkit.fluxcd.io/substitute: disabled`, as would any custom Alertmanager
  template. The Probe's targets and the alert recipient are substituted as usual.
- **Only what carries `office.haaijer.dev/monitoring: "true"` is selected**, by our
  Prometheus and, under `external`, by theirs: an upstream chart's ServiceMonitor is not
  collected because it exists.
- **Out of scope:** dashboards (the inventory's rule still holds, so no vendored JSON), log
  collection, tracing, and node configuration. The kubelet's shutdown settings are a
  `preflight.py` check, not an alert.

## What this layer is for
`monitoring/` is where the platform states what "working" means, as rules and probes. These
belong there later, each with its metric source if it needs one:
- **Checks specific to one app**, as a component per app, emitted when that app is enabled
  (the control plane already knows which are). Examples: Drive's WOPI discovery present in
  its cache, the symptom of the maintenance week; Docs' collaboration websocket accepting a
  connection; LiveKit's TURN port answering. They sit here and not in `apps/<app>/` so that
  monitoring stays a leaf.
- **Backup freshness**, once the platform takes backups. It takes none today: there is no
  CNPG `ScheduledBackup`, and Garage's data is not copied anywhere. The rule (last
  successful backup older than a day) comes with the backups, together with CNPG's
  PodMonitor.
- **Datastore saturation.** The broker runs `noeviction`, so a full broker refuses writes
  instead of shedding keys. That needs a Valkey exporter and a memory-against-`maxmemory`
  rule. OpenSearch disk watermarks are the same kind of check.
- **The dead-man's switch.** `Watchdog` routed to an external heartbeat, once the schema
  takes a URL for it.

Two things do not belong here. Dashboards would be a separate, optional layer if they ever
come. Log-derived signals, such as kernel I/O errors or a kubelet that failed to take its
logind lock, need log collection, and that is a different decision and a much heavier stack.

## Reasoning
kube-prometheus-stack is the heaviest option on a single-node VPS, but its CRDs
(ServiceMonitor, PodMonitor, PrometheusRule, Probe) are what upstream charts emit and what
existing clusters already run. `external` only works because the platform speaks those CRDs.
A lighter stack with its own resource types would make `external` a translation layer.

A separate layer earns its place three ways. The CRDs must exist before the rules, the same
ordering problem `0112` solved with two layers. `external` needs the rules without the
stack. And as a leaf, monitoring can fail, be switched off, or be rebuilt without touching
what users run. The surround-generated design gave that up: a Probe in every app's surround
would make every app wait for the monitoring CRDs, so a broken Prometheus chart would stall
the platform. The control plane already holds the host list, so generating the probes
centrally loses nothing.

"Nothing collected unless a rule reads it" is what keeps the stack small, and it is a test a
reviewer can apply: a new ServiceMonitor without a rule that reads its series is refused.
cAdvisor and node-exporter are most of a default install's series, and the control-plane
scrapes are much of the rest. None of the alerts above reads them.

Weight, measured on the reference cluster (about 50 pods, every app) 20 minutes after the
install, with kube-state-metrics and the kubelet allowlisted to the series the rules read:
- **Series:** 1,055 in the head.
- **Memory:** 54 Mi for Prometheus, 68 Mi for the other four pods combined.
- **CPU:** 14m in total.
- **Disk:** under 1 GB over the 7 days at that rate; 6 Gi of volumes are reserved.

The estimate before the allowlists was 5–15k series and 250–450 Mi. A 24-hour measurement,
over head compactions, replaces these figures before this is accepted.

Against `./measure.py render --size small` (3.47 cores and 21.2 Gi requested, platform and
apps), the requests (35m and 160 Mi) are about 1 % of either. `small` is also the size most
likely to be a single unattended VPS, the install that most needs an alert, so making
monitoring start at `medium` would cut it from the clusters that need it most. The figures
are replaced by measured ones before this is accepted.

`external` exists because half the installs go onto an existing cluster (`0112`), and there
the alternatives are both wrong. `platform` runs a second Prometheus, which pages nobody the
organisation's on-call watches, and a second operator fights over the CRDs. `off` leaves the
platform unwatched. The split into two layers is needed anyway, so `external` costs one test
case, one preflight check and a section of `docs/install.md`. It is kept narrow, with no
routing and no guarantees about what the cluster collects, so that the platform makes no
claims about a stack it does not run.

Email through the existing relay is the receiver every install already has. A cluster on the
placeholder relay (`smtp.configured: false`) still collects and evaluates alerts, but cannot
deliver them, and `preflight.py` warns about that combination.

## Consequences
- Upgrading to the release that carries this installs monitoring on every cluster that does
  not set `mode`. That is the intent, and it goes in the CHANGELOG as a behaviour change, with
  its resource cost per size.
- A cluster that already runs a Prometheus operator must choose `external`, or remove its own
  operator first: two operators fight over the same CRDs. `preflight.py` refuses `platform`
  when it finds monitoring CRDs it did not install. The reference cluster had an unused
  operator (v0.90.1, no objects of any of its CRDs); it was removed on 2026-10-19, so the
  reference cluster runs `platform`.
- `control-plane` grows the `monitoring` block in its schema, two cluster-vars (the mode, and
  the alert recipient and the probe targets derived from `TLS_HOSTS`) and the two layers. `platform-app` does not
  change. Every `cluster-*` case gets a golden update. `tests/cases/` gains a case with
  `mode: external` and one with `mode: none`, and `tests/schema.py` checks that `email` is
  refused with `external`. A check asserts that no object outside `cluster/monitoring/` and
  `monitoring/` uses a `monitoring.coreos.com` kind, and that no Kustomization depends on
  either layer.
- `policy/config` gains a rule that the HelmReleases under `platform/valkey/` and
  `platform/opensearch/` set drift detection.
- Like every layer, `monitoring` is `keep`. Switching the mode to `none` leaves the stack
  running until someone runs `flux delete ks`.
- The Watchdog only helps if something outside the cluster expects it. Until the schema
  takes a heartbeat URL, wiring it up is the organisation's job, documented in
  `docs/install.md`.
- Without node-exporter, host trouble that the kubelet does not turn into a condition goes
  unseen, such as a full disk the kubelet does not manage or a failing NIC. That is the
  price of the rule above; node-exporter comes back with the first alert that reads it.
- Signals that never become a metric stay unwatched: a kernel I/O error, a kubelet that
  failed to take its logind lock. Those need log collection, which is deferred.
