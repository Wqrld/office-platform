# Identity — Keycloak

Operator and server are one release. `vendor/keycloak-operator/` is a verbatim copy of
`keycloak/keycloak-k8s-resources` at the version `vendor/keycloak-operator/kustomization.yaml` pins; everything we change about it is in
`vendor/keycloak-operator/kustomization.yaml`. `vendor/keycloak-operator/update.sh` checks
for a newer tag and, if there is one, re-downloads all five files and bumps the version
comment in the same commit — run by hand, or weekly by CI alongside updatecli
(`.github/workflows/upstream-updates.yaml`). Never hand-edit the five files themselves.

The operator watches only its own namespace (`JOSDK_WATCH_CURRENT`), so it and the
`Keycloak` CR must share one.

## The realm is reconciled, not imported

The operator's KeycloakRealmImport is import-once: it runs `kc.sh import --override=false`,
hardcoded, and never re-runs, so an edited realm file used to change nothing and every new
client or relay needed a script run by hand on every cluster. The realm now lives in the
`platform-tenants` chart instead:

- `charts/platform-tenants/files/realm.yaml` — every realm setting, commented;
- one client per `oidc` entry in `charts/control-plane/apps.yaml`, from three shapes
  (`lasuite`, `login`, `resource-server`) rather than a copied block per app;
- a `realm-<hash>` Job in this namespace that runs keycloak-config-cli with both. The name
  is a hash of what it applies, so any change is a new Job, which runs once.

**Adding a client is adding an `oidc` entry.** Nothing to run: the next release's Job
creates it, with the secret from `oidc-client-<app>` (generated by the same chart).

What the Job may do, verified against a Keycloak 26.7.3 seeded from prod's realm export:
it creates missing clients, updates the ones listed (secrets included — they are the
generated values, so unchanged), sets the realm settings and `smtpServer`, and a second run
with the same input changes nothing (its checksum is stored in the realm's attributes).
What it may not: every managed type is `no-delete`, so a client made in the admin console,
the client of an app that left the table, and every user are left alone — and it never
touches users at all, because the import has no `users` key.

A setting changed in the admin console that the file also sets is overwritten by the next
Job. Change it in `files/realm.yaml`.

`platform/identity/realm.yaml` is a stub, kept one release so its CR can be marked
`prune: disabled` before it leaves git (platform/kustomization.yaml). Deleting the CR would
not delete the realm — the operator's `KeycloakRealmImportController` implements no
cleanup, and the CR carries no finalizer; its Job and `keycloak-office-realm` Secret go with
it — but that is not a thing to find out on prod.

## Users are not in the realm

Create them in the admin console; they get `default-roles-office` there. An imported user
would not: the import takes the representation literally, and without `realmRoles` the
access token has no `aud: account` and the Account Console 401s with no server-side event.
An organisation's users are its own anyway.

## Rotating the relay

`smtp-credentials` is re-read into this namespace hourly (`smtp.yaml`), but a Secret's value
is not part of the Job's hash, so the realm takes a new relay password when the Job next
runs. Run it now:

```sh
kubectl -n office-identity delete job -l app.kubernetes.io/instance=tenants
flux reconcile helmrelease tenants -n office-data --force
```

Confirm by sending, not by looking: Keycloak masks the SMTP password on read, so the admin
console's **Realm settings → Email → Test connection** is the check, followed by a real
"Forgot password?" from the login page.

The relay account itself is applied by hand into `office-data` once — `docs/install.md`
step 3. Nothing about it is in git, not even the host.

## Substitution syntax

`files/realm.yaml` is read by keycloak-config-cli, whose substitution is `$(env:NAME)`,
resolved from the Job's environment. Keycloak's own `${NAME}` placeholders are not used
anywhere any more — they belonged to the import, where Flux's identical `${NAME}` syntax
forced `$${NAME}` escapes. Neither Helm nor Flux touches `$(env:…)`.

## First rollout on a live realm

The first release carrying this runs the Job against a realm that was imported. Before it:
prod's realm, users (with hashes, in the database dump) and every Secret are backed up at
`/root/office/backups/20260930-172857-pre-reconcile/` (its MANIFEST.md says how to restore).

1. `kubectl -n office-identity get job -l app.kubernetes.io/instance=tenants -w` — one
   `realm-<hash>` Job, Complete within a minute; `kubectl logs job/realm-<hash>` ends in
   `keycloak-config-cli ran in …`.
2. What changes: the Messages client gains `frontchannel.logout.session.required: "false"`
   and `post.logout.redirect.uris` (it was copied from Docs without them); every other client
   and realm setting already equals the file, so it is rewritten to the same value. The
   realm gains keycloak-config-cli's state attributes.
3. Log in to each app once; log out of Messages and see it land back on its own page.
4. Rollback: the realm is in the `keycloak` database. Scale the Keycloak StatefulSet to 0,
   `pg_restore --clean --if-exists -d keycloak` the dump, scale back — every session ends.
   A single client is quicker: re-POST it from `keycloak-clients-live.json` in the backup.

## Internal vs external URLs

`hostname.backchannelDynamic: true` is the whole mechanism. Verified on this cluster:

```
$ curl https://id.haaijer.dev/realms/office/.well-known/openid-configuration
  issuer                 https://id.haaijer.dev/realms/office
  authorization_endpoint https://id.haaijer.dev/...

$ curl http://keycloak-service.office-identity.svc:8080/realms/office/.well-known/…
  issuer                 https://id.haaijer.dev/realms/office
  token_endpoint         http://keycloak-service.office-identity.svc:8080/...
```

Applications must consume both halves: browser endpoints external, backend endpoints
internal. `charts/platform-deps/templates/_oidc.tpl` renders it; `apps/docs/deps.yaml` is the worked example.

## Admin access

`bootstrapAdmin.user.secret` only applies the first time a Keycloak starts against an
empty database. On this cluster the CR was created before that stanza existed, so the
operator generated its own `keycloak-initial-admin` — and deleted it when the stanza
appeared, stranding the account. Recovery, should it happen again:

```
kubectl -n office-identity exec keycloak-0 -- \
  env KC_HTTP_PORT=8123 KC_HTTP_MANAGEMENT_PORT=9123 \
  /opt/keycloak/bin/kc.sh bootstrap-admin user --username tempadmin \
    --password:env KC_BOOTSTRAP_ADMIN_PASSWORD --no-prompt
```

The default ports must be overridden or the command collides with the running server and
fails with `Address already in use`.
